Задача: создать свой брокер сообщений, с хранением сообщений в PostgreSQL и клиентом (publisher+subscriber) на C#

Проектирование схемы БД. Создайте таблицу tasks, которая будет служить хранилищем очереди. Опирайтесь на свою предметную область.
Реализация Продьюсера (1 сервис)
Продьюсер должен в цикле генерировать события.
Задача: Реализовать вставку задач с разным весом (приоритетом). Например: 80% обычных задач, 20% критических.
Особенность: Используйте преимущество транзакционности PostgreSQL — вставляйте задачу в очередь в рамках одной транзакции с какой-либо фиктивной «бизнес-логикой».
Реализация Консьюмеров (2 сервиса)
Запустите два независимых процесса-воркера, которые будут конкурировать за задачи.
Логика: Воркер берет задачу, переводит её в статус Running, «обрабатывает» (имитация через sleep) и помечает как Completed или Failed.

Нагрузка и мониторинг Лага
Запустите продьюсера на высокую интенсивность (например, 100–500 вставок в секунду), чтобы очередь начала расти.
Лаг очереди: Напишите SQL-запрос, который показывает разницу между now() и временем created_at самой старой задачи в статусе Ready. Это покажет, как долго задачи ждут выполнения.
Пропускная способность: Посчитайте, сколько задач в секунду обрабатывают оба консьюмера суммарно.

Дополнительно (за пару баллов)
Механизм Retry: Если задача завершилась ошибкой, воркер должен увеличить счетчик attempts и перенести scheduled_at на 5 минут в будущее (exponential backoff).
Оптимизация (Notify): Вместо постоянного опроса базы (polling) раз в секунду, используйте механизм LISTEN / NOTIFY, чтобы продьюсер «будил» консьюмеров при появлении новой задачи.
Борьба с Bloat: Настройте агрессивный autovacuum для таблицы очереди или запустите ручной VACUUM ANALYZE во время теста, чтобы увидеть, как «раздувание» таблицы влияет на время выборки задач.

Использовать следующие детали реализации:

Для реализации очереди обычно создается специальная таблица (например, jobs или task_queue), которая служит буфером задач.
Структура таблицы: Она должна содержать как минимум ID задачи, полезную нагрузку (payload), текущий статус, время планируемого выполнения (scheduled_at) и количество попыток (attempts).
Основные статусы: Обычно используются статусы Ready (готова к работе), Running (выполняется), Completed (успешно завершена) и Failed (ошибка).
Жизненный цикл:
Producer вставляет строку в таблицу в рамках бизнес-транзакции.
Consumer (воркер) выбирает задачу, переводит её в статус Running и фиксирует своего worker_id.
После выполнения воркер либо удаляет строку, либо обновляет статус на финальный (Completed).

Эффективность очереди напрямую зависит от индексов, минимизирующих количество сканируемых строк:
Составной индекс на (status, id) или (status, scheduled_at): Позволяет быстро находить только те задачи, которые находятся в статусе Ready и чье время выполнения уже наступило.
Частичные индексы (Partial Indexes): Можно создать индекс только по незавершенным задачам (WHERE status < 2). Это значительно экономит место, так как индекс не будет раздуваться из-за миллионов уже выполненных задач.
Индекс по приоритету: Если задачи имеют разную важность, приоритет должен быть включен в индекс перед временем планирования для корректной сортировки.

Для надежной работы системы необходимо предусмотреть сценарии ошибок:
Retry (повторы): В таблицу добавляется колонка attempt (счетчик попыток). При ошибке воркер увеличивает счетчик и пересчитывает время следующего запуска (delayed_to / scheduled_at), используя, например, экспоненциальную задержку.
Visibility Timeout / Stuck tasks: Чтобы задачи не висели вечно в статусе Running (если воркер упал), используется поле expected_status_change_time или updated_at.
Фоновый процесс (Cleanup): Отдельный процесс периодически ищет задачи, которые слишком долго находятся «в работе», и сбрасывает их статус обратно в Ready, чтобы другой воркер мог их подхватить.

Пример

FROM tasks
WHERE status = 'ready'
    AND scheduled_at <= now()
ORDER BY priority DESC, created_at
